# 发布与插件市场收录

本文记录 DSH Capsule（`@dsh-capsule/adapter`）的发布流程与各插件市场的收录方式，供维护者照做。
发布前请先阅读根目录 `AGENTS.md`，并以其中最新项目决策为准。

## 1. 发布形态

- npm 包：`@dsh-capsule/adapter`（scoped，`publishConfig.access = public`）。
- 包内提供：`dist/`（构建产物）、`client.js`（DSH Web 客户端半边）、`cordis.patch.yml`（bundle patch）。
- 包 `name` 必须与 `cordis.patch.yml` 的 `name` 以及 `client.js` 的模块 id 一致，均为 `@dsh-capsule/adapter`。
- 运行时零依赖：宿主接口通过 Cordis `ctx` 注入，生产源码不 import 任何 `@deepseek-ai/*` 包（仅测试使用）。
- `engines.dsh` 声明支持的 DSH 范围：`>=0.1.5-0 <0.3.0`；`engines.node` 为 `>=22`。

## 2. 发布前检查

```bash
pnpm install --frozen-lockfile
pnpm build
pnpm test
```

然后在 `adapter/` 目录检查发布内容（不真正发布）：

```bash
npm pack --dry-run
```

预期包内只有：`dist/**`、`client.js`、`cordis.patch.yml`、`README.md`、`LICENSE`、`package.json`。
`src/`、测试文件、`tsconfig*.json`、`node_modules` 不应进入 tarball（由 `files` 字段约束）。

版本规则：改代码必须 bump `adapter/package.json` 的 `version` 并推送；市场用版本做更新检测。
首发为 `0.1.0`。

## 3. 发布到 npm

```bash
cd adapter
npm publish --registry=https://registry.npmjs.org
```

- 发布前需登录 npm 且账号对 `@dsh-capsule` scope 有发布权限（scoped 包要求该 scope 属于当前账号或其组织）。
- `.npmrc` 若指向镜像（如 `registry.npmmirror.com`），发布时必须显式带 `--registry=https://registry.npmjs.org`。
- `prepack` 会在打包前执行 `tsc`，确保 tarball 里的 `dist` 与源码一致。
- 发布后验证：

```bash
npm view @dsh-capsule/adapter version
npm view @dsh-capsule/adapter dist.tarball
```

## 4. GitHub 仓库设置

收录依赖仓库公开可访问且带有 DSH 识别信号。

- Topics（仓库页 → Settings → Topics）：至少 `dsh-plugin`；建议同时加 `dsh`、`deepseek-harness`、`cordis-plugin`、`typescript`。
- Description：填写一句话简介（当前为空），例如：
  `Short-lived authorization leases, do-not-disturb windows and local authorization decisions for DeepSeek Harness.`
- License：MIT（已有）。
- README 必须包含可执行的安装命令（已包含 `dsh plugin --profile web add @dsh-capsule/adapter`）。

## 5. 各市场收录方式

| 市场 | 入口 | 机制 | 需要人工做什么 |
| --- | --- | --- | --- |
| dsh.so | <https://www.dsh.so/submit/> | 提交仓库或 npm 包 → 服务端重新抓取并安全扫描 → 后台 issue 审核合并 | 在网页粘贴 `github.com/whDonline/dsh-capsule` 或 `@dsh-capsule/adapter`，通过检查后点 Submit |
| DSH-Plugins-Marketplace | <https://github.com/bradeGithub/DSH-Plugins-Marketplace> | CI 每约 2 小时扫描 GitHub `dsh-plugin` topic，自动写入静态索引 | 只加 topic，无需申请 |
| dshbase.com | <https://dshbase.com/plugins/directory/> | 社区目录，按仓库/topic 索引 | 加 topic；如未被收录可在站点联系页提交 |
| awesome-dsh-plugin | <https://github.com/awesome-dsh-plugin/awesome-dsh-plugin> | 人工维护的精选列表 | 向该仓库提 PR，在对应分类加一行 |

dsh.so 的验证等级（L1–L5）：

- L1 仓库可访问且有 README；
- L2 manifest 完整（name / license / description）；
- L3 能从 manifest 解析安装命令并声明 DSH 版本要求（本包的 `dsh.bundle` + `engines.dsh`）；
- L4 在隔离沙箱里真实执行安装命令；
- L5 DSH 加载插件并通过冒烟检查（web 启动、HTTP 可用、插件清单 active）。

L4 / L5 是按 DSH 版本记录的运行结果，DSH 升级后旧结论会标为 stale 并重新排队。

## 6. 安全与披露

本包不访问云端、不收集遥测、不需要 API Key；审计默认只写本机
`<用户目录>/.dsh/capability-guard/audit.ndjson`（`auditFile` 可覆盖，`persistAudit: false` 关闭）。
`adapter/package.json` 的 `disclosure` 字段与 `adapter/README.md` 的「安全边界」一节是给市场披露层与审核人看的，
修改能力边界时必须同步更新。

## 7. 发布后回归

```bash
dsh plugin --profile <一个新 profile> add @dsh-capsule/adapter
dsh --profile <profile> --dump-config
```

确认组合树中出现 `capability-guard` 层，再启动 DSH，检查：

1. 输入框左侧出现 Guard 模式 chip；
2. 会话内第三个 tab「能力授权」可打开；
3. 一次原生审批批准后，授权列表出现 Lease 与倒计时；
4. 撤销后再次执行同一操作会重新触发原生审批。

宿主端代码更新后必须重启 DSH，不能依赖 profile 配置 HMR。
