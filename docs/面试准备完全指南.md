# 第 0 章：给完全不懂的你先补三件事

## 0.1 什么是 Agent？它和普通程序有什么不同？

**普通程序**：你写 `删除文件 A`，它就删 A。做什么完全由你的代码决定。

**Agent**：你给它一个**目标**（"把这个项目的测试修好"），它自己决定**要用哪些工具、按什么顺序用**。它会：
1. 思考"我该先看看测试报什么错"
2. 调用 `pwsh` 工具执行 `pnpm test`
3. 看到错误，思考"好像是类型不对"
4. 调用 `read` 工具读文件
5. 调用 `edit` 工具改代码
6. 再跑测试

**关键区别**：第 2~5 步**不是你的代码决定的，是模型现场决定的**。

这就带来一个全新的问题：**你怎么知道它下一步要干什么？**

---

## 0.2 为什么 Agent 需要"权限系统"？

因为 Agent 能做的事**太危险了**。它手上有一堆工具：

| 工具 | 能干什么 | 危险在哪 |
|---|---|---|
| `pwsh` | 执行任意命令 | 能删库、能联网、能读所有文件 |
| `write` / `edit` | 写任意文件 | 能改你的源码、能改配置 |
| `web_fetch` | 访问任意网址 | 能把你本地的数据发出去 |

如果你给 Agent 无限制权限，一个提示词注入（Prompt Injection，见名词表）就能让它把你的 SSH 私钥发到攻击者服务器。

**所以 Agent 平台（比如 DeepSeek Harness）会加一层"闸门"**：

- **allow（放行）**：这个操作没问题，直接做
- **deny（拒绝）**：这个操作禁止，直接报错
- **ask（询问）**：这个操作有风险，**问一下用户**

**`ask` 就是本项目的舞台。**

---

## 0.3 用户的真实感受：审批疲劳（Approval Fatigue）

想象你用 Agent 干活：

```
Agent: 我想执行 Set-Content C:\other\file.txt
系统:  ⚠️ 需要批准 [允许] [拒绝]
你:    允许 ✅
Agent: 我想执行 Get-Content C:\other\file.txt
系统:  ⚠️ 需要批准 [允许] [拒绝]
你:    允许 ✅
Agent: 我想执行 New-Item C:\other\dir
系统:  ⚠️ 需要批准 [允许] [拒绝]
你:    ……又是我？允许 ✅
（20 次之后）
你:    算了，我直接开全权限模式吧
```

**这就是核心矛盾**：
- 每次问 → **人累死**，最后用户会关掉所有审批（等于没做安全）
- 不问 → **危险**，Agent 可以随便删你的东西

DSH 原生只有这两种极端：**一次一问**（`allowed-once`），或者**整个会话放开**（permission preset）。

**中间那层是空的。** 这正是本项目要补的洞。

# 第 1 章：项目定位 · 真实问题 · 真实场景

## 1.1 一句话定位

> **DSH Capability Guard 是给 DeepSeek Harness 补上「授权中间层」的插件：让一次人工批准变成一段有边界、会自动过期、能撤销、有审计记录的短期权限。**

## 1.2 真实问题：DSH 的权限模型缺一层

DeepSeek Harness（后面简称 DSH）的权限体系只有两层：

| 层级 | 粒度 | 生效方式 | 问题 |
|---|---|---|---|
| `permission-presets` | **会话级**（sandbox 模式 + approval 策略的组合） | 一次切换，整个会话生效 | **太粗**：一放开就是整个会话 |
| `allowed-once` | **单次调用** | 每次弹窗，人点一下 | **太细**：每次都问 |

```
粗 ──────────────────────── 空 ──────────────────────── 细
permission-presets      【本插件补这里】          allowed-once
"这个会话全放开"         "这个工具这类操作           "就这一次"
                        在 5 分钟内有效"
```

**别人的方案是用静态配置补这层**：
- Claude Code 用 `permissions` 配置块
- Codex CLI 用 sandbox 配置文件

**它们的共同缺陷**：静态 = 写死在文件里。改配置要重启、**没有过期、没有自动回收、没有"什么时候放宽过"的记录**。

**本项目的方案是运行时补**：授权是一个**活的对象**（Lease），有签发时间、过期时间、状态机、可以撤销、会被审计。

## 1.3 真实场景：我自己的开发过程就是靶场景

**这一段是全文最有说服力的部分，面试务必讲。**

在开发这个插件的 7 轮迭代中，真实发生的事：

```text
我（AI Agent）需要反复运行同一个命令来验证测试：
  node .\node_modules\vitest\vitest.mjs run

但当前文件策略是 workspace-write，这个命令的内部子进程需要更高权限
→ 每一次执行都被沙箱拒绝
→ 我每一次都要单独申请提权（需要用户批准）
→ 十几次调用 = 十几次批准
```

**更糟的一次**：我执行 `pnpm -s test`，它触发了 pnpm 的重装流程，**把 `node_modules` 整个清空了**，我不得不先修环境再继续。

**如果本插件当时生效**：
1. 我批准一次 `pwsh → danger-full-access`，TTL 设 300 秒
2. 后续十几次 `vitest` / `tsc` 调用**全部零点击**
3. 300 秒后**自动回滚**到我批准前的档位

**这就是"把 N 次点击压缩成 1 次"，而且是真实的 N，不是编的。**

### 场景二：企业级合规审计

企业采购 Agent 平台时，安全团队会问：

> "这个 Agent 在什么授权下、访问了什么、授权持续多久、谁批的、能不能查、能不能提前收回？"

DSH 原生只记录 `approval/asked` 和 `approval/decided`——**没有 scope、没有 TTL、没有撤销记录**。

本插件提供完整的治理事件流：

```text
SANDBOX_MODE_RAISED                  权限何时被放宽、放宽到哪一档
SANDBOX_MODE_RESTORED                何时自动收回
SANDBOX_MODE_SKIPPED_USER_OVERRIDE   检测到用户手动改过，主动放弃回滚并交还控制权
```

**"放宽"和"收回"都有记录**，这是合规场景的刚需。

### 场景三：多 Agent / 子 Agent 权限隔离

父 Agent 批准过的权限，**不该自动流转给子 Agent**。本项目严格遵守 DSH 的硬边界（见 4.1 节）。

## 1.4 这个项目**不**解决什么（务必主动说）

**面试官最欣赏的是"知道自己的边界在哪"。** 以下三条要主动讲，不要等他问：

| 不解决 | 原因 |
|---|---|
| **不防恶意插件** | Managed Mode 是 SDK 约定 + 代码评审保证，**不是运行时强制**。同进程插件可以直接读 `process.env`、自己 `fetch`、自己调 `setSandboxMode` 绕过 |
| **子 Agent 无法受益** | DSH 把子 Agent 的 approval policy **钉死为 `never`**（`dsh-subagent:566-571`），它连"问"的机会都没有 |
| **不提供 OS 级隔离** | 没有容器、没有独立进程。运行时强制边界是 **DSH 进程本身** |

**正确的自我定位一句话**：
> "它是**防误用 + 集中审计**的机制，不是防恶意的隔离边界。"

# 第 2 章：名词表（来龙去脉）

> 每个词都给：**是什么 → 为什么需要 → 本项目怎么用**。面试时被问名词，能答出"为什么需要"就赢了。

## 2.1 Agent 基础概念

### Agent（智能体）
**是什么**：能自主决定调用哪些工具、按什么顺序调用，以达成目标的 AI 程序。
**为什么需要**：传统程序只能执行预设流程，无法应对开放式任务。
**本项目关联**：Agent 是"权限的申请方"，本项目管的就是 Agent 能用工具做什么。

### Tool（工具）
**是什么**：Agent 可以调用的一个能力单元，比如 `pwsh`（执行命令）、`read`（读文件）、`web_fetch`（抓网页）。
**为什么需要**：模型只会生成文本，必须有工具才能和真实世界交互。
**本项目关联**：权限的最小单位就是"某个 Tool 的某次调用"。

### Tool Pipeline（工具管线）
**是什么**：一次工具调用从"模型提出"到"真正执行"之间的流水线，中间有多个可以插手的环节。
**为什么需要**：安全策略、日志、超时、重试等横切关注点需要统一入口。
**本项目关联**：**本插件就是插在这条管线上的四个环节里**（见第 3 章）。

### Prompt Injection（提示词注入）
**是什么**：攻击者把恶意指令藏在 Agent 会读到的内容里（网页、文件、Issue 评论），让 Agent 执行非预期操作。
**为什么需要知道**：这是 Agent 安全的第一大威胁。
**本项目关联**：权限边界是缓解手段之一——即使模型被骗，它能做的也受授权范围限制。

---

## 2.2 DSH / Cordis 平台概念

### DeepSeek Harness（DSH）
**是什么**：DeepSeek 官方的 Agent 运行框架（Harness = 马具，即"驾驭模型的外壳"）。提供工具管线、审批、沙箱、会话、模型接入等。
**版本情况**：本机安装版为 rc.1/rc.2，处于 **Developer Preview**，快速迭代。
**本项目关联**：本插件是 DSH 的一个**独立插件**，**不修改 DSH 源码**。

### Cordis
**是什么**：DSH 底层的**插件框架**（DI 容器 + 事件系统 + 服务注册）。DSH 的所有功能都是 Cordis 插件。
**为什么需要**：让功能可以自由组合、按需加载、互相依赖。
**本项目关联**：本插件以 Cordis 插件形态接入，用它的**事件瀑布**和**服务系统**。

### Service（服务）
**是什么**：Cordis 里的"具名能力"，比如 `ctx.tools`、`ctx.approval`、`ctx.credentials`。插件可以注册自己的服务给别人用。
**本项目关联**：本插件注册 `ctx.capabilities` 服务给 Managed Extension 调用。

> ⚠️ **重要 API 事实（我踩过的坑）**：Cordis 中**未经 `inject` 声明的服务，不能用属性访问**（`ctx.foo` 会抛 `cannot get property "foo" without inject`）。必须用 **`ctx.get("foo")`**（缺失时返回 `undefined`，不抛错）。这条在真实 Cordis 下必然触发，但用假 ctx 的单元测试**发现不了**。

### inject（依赖声明）
**是什么**：插件声明"我需要 tools 和 approval 服务，它们就绪后再激活我"。
**本项目关联**：`export const inject = ["tools", "approval"]`。
**关键性质**：Cordis 的 `inject` 是**硬依赖**——服务不存在，插件根本不激活。

### waterfall（瀑布式事件）/ prepend
**是什么**：Cordis 的中间件机制。每个监听器收到 `next` 回调，调用它就把决策权交给下一个监听器；**不调用就直接"认领"（claim）整个事件**。
**为什么需要**：一次事件可能有多个插件都想插手，需要明确顺序和归属。
**本项目关联**：审批事件 `approval/request` 就是瀑布。**这里有个致命细节（见 4.2 节）**。

### 事件名（本插件挂的四个）
| 事件 | 时机 | 本插件做什么 |
|---|---|---|
| `tools/pre-execute` | 工具执行**前**，决定 allow/deny/ask | 只接管下游返回 `ask` 的调用（复用 Lease） |
| `tools/execute` | 工具**即将执行**时，参数完整可用 | 识别沙箱升级、记录待批准上下文 |
| `approval/request` | 需要人工审批时 | 观察结果，`allowed-once` 后签发 Lease |
| `tools/result` | 工具执行**后** | 记录结果、标记上下文已结算 |

## 2.3 权限与安全概念

### Approval（审批）
**是什么**：DSH 在工具执行前询问用户的机制，结果是四种之一：
- `allowed-once`：**唯一**的批准值（"就这一次"）
- `rejected`：用户明确拒绝
- `cancelled`：请求被取消
- `unavailable`：没有可用的答话器（**fail-closed**）

**本项目关联**：只有 `allowed-once` 才会签发 Lease。

### Lease（租约）
**是什么**：本项目引入的核心对象。一次授权不是"永久允许"，而是"**在某个范围内、某段时间内允许**"。
**为什么叫租约**：借用了分布式系统的概念（如 Chubby/etcd 的 lease）——**授权是有期限的、需要续期的**。
**本项目关联**：

```text
Lease = Session（哪个会话） × Tool（哪个工具） × Scope（哪类操作） × TTL（多久过期）
```

### Scope（授权范围）
**是什么**：Lease 覆盖的"多大范围"。本项目有五种：

| Scope 模式 | 含义 | 类比 |
|---|---|---|
| `exact-arguments`（默认） | 参数**完全一致**才能复用 | "只许你买这一瓶可乐" |
| `fields` | 只按指定字段匹配 | "只许你买这个牌子的任何饮料" |
| `tool` | 该工具的所有调用 | "这个超市你随便买" |
| `sandbox-escalation` | 按 `(工具, 目标权限档位)` | "你可以在 5 分钟内进后厨" |
| `managed` | 业务语义（provider + resource + action） | "只许你操作 A 仓库的 Issue" |

### TTL（Time To Live，存活时间）
**是什么**：授权多久后自动失效。本项目默认 60 秒，上限 1800 秒。
**为什么需要**：**权限不应该永久有效**。最小权限原则要求权限尽可能短暂。

### Fail-Closed（故障关闭）
**是什么**：出现任何不确定情况时，**拒绝**而不是放行。
**为什么需要**：安全系统的默认姿态应该是"不信任"。反面是 fail-open（出错就放行），那是灾难。
**本项目关联**：贯穿全项目。Scope 解析失败 → 不签发；TTL 非法 → 不签发；审批结果不是 `allowed-once` → 不签发；服务缺失 → 降级为不提升权限。

### Sandbox（沙箱）/ Sandbox Mode（沙箱档位）
**是什么**：限制 Agent 能改哪些文件的机制。DSH 有三档：

| 档位 | 含义 |
|---|---|
| `read-only` | 只能读 |
| `workspace-write` | 能改工作区内的文件 |
| `danger-full-access` | 不限制 |

**本项目关联**：**这是本项目最核心的机制依赖**（见 4.2 节）。

### Escalation（升级）
**是什么**：当沙箱拒绝了操作，模型可以**带上理由重新请求更高的权限**（参数 `sandbox_permissions` + `justification`）。
**本项目关联**：**这是 DSH 里唯一真实的审批入口**（这个发现改变了整个设计，见第 5 章）。

### Credential（凭证）/ Credential Broker（凭证代理）
**是什么**：调用外部服务需要的密钥（如 GitHub Token）。Broker 是"代持凭证的中介"：插件不直接拿密钥，而是提交一个**业务操作请求**，由 Broker 代为调用。
**为什么需要**：减少密钥分发面——密钥只在一个可信路径里被解析。
**本项目关联**：亮点三。

### Least Privilege（最小权限原则）
**是什么**：任何主体只应拥有完成当前任务所必需的最小权限。
**本项目关联**：整个项目的理论出发点。

## 3.2 两种工作模式

### 模式一：Universal Mode（通用模式，亮点一 + 亮点二）

**适用**：任何**已存在**的工具，**零代码改造**。

**做什么**：在它触发审批时，把"这一次批准"升级成"一段时间的授权"。

```text
用户批准一次
   ↓
签发 Lease（绑定 Session × Tool × Scope × TTL）
   ↓
后续同类调用自动放行（不再弹窗）
   ↓
TTL 到期 / 主动撤销 → 自动失效并回滚权限档位
```

### 模式二：Managed Mode（托管模式，亮点三）

**适用**：按本项目 SDK 编写的新扩展。

**做什么**：扩展**不接触密钥**，只提交业务操作；由 Broker 统一校验并调用外部 API。

```text
Extension: "帮我读 org/repo 的 issue #42"
   ↓
Guard: 校验 Lease + 重算资源（防伪造）+ 解析凭证
   ↓
Provider: 真正调用 GitHub API
   ↓
返回业务结果（凭证从未离开 Guard）
```

## 3.4 关键设计原则（面试可背）

| 原则 | 含义 | 代码体现 |
|---|---|---|
| **不替代审批** | Guard 只增强 `ask`，不覆盖 `deny`，不重新发明审批 | `handlePreExecute` 先 `next()` 拿下游决策，`deny` 直接透传 |
| **确定性 Scope** | 安全边界来自确定性规则，**不让 LLM 猜** | `justification`（模型自由文本）绝不参与 Scope 计算 |
| **Fail-Closed** | 任何不确定就拒绝 | Scope 解析失败不签发、TTL 非法不签发、服务缺失不提升 |
| **短期权威** | 权限必须有边界 | `Session × Tool × Scope × TTL` |
| **Secret 不出 Guard** | 凭证不写日志/审计/错误信息 | Broker 出口做错误脱敏；审计类型层面就不含参数原文 |
| **绝不合成 outcome** | 审批结果只能来自人/机答话器 | `handleApprovalRequest` 全方法只调用一次 `next()` 并原样返回 |
| **单一时间源** | 时间判定只有一个来源 | 有效性由 `LeaseManager.isLive(id)` 用自身时钟判定 |

## 3.5 一次完整的沙箱升级 + 复用（时序图）

这是**本项目最核心的链路**，面试必讲：

```text
第一次调用（无人批准过）
──────────────────────────────────────────────────────
模型: 我要执行 Set-Content C:\other\x.txt
  + sandbox_permissions: "danger-full-access"
  + justification: "需要写入工作区外"

① tools/pre-execute
   Guard 调 next() → 下游落底是 allow（DSH 原生！）
   → 不是 ask → Guard 透传（PASSTHROUGH_ALLOW）

② tools/execute
   Guard 识别到升级参数 → 解析出目标档位 danger-full-access
   → 查 Lease：没有 → 记录"待批准上下文"（按 callId 关联）
   → 原样执行下游（不改变结果）

③ 工具内部（pwsh 的代码）
   发现自己需要写工作区外 → 调 approveEscalation
   → ctx.approval.request({agent, toolName, callId, reason})
   → 注意：这个请求【不含 arguments】！

④ approval/request
   Guard 观察结果（必须调 next()，绝不能自己返回"批准"）
   用户点了 allowed-once
   → 签发 Lease（kind = "sandbox-mode"，Scope = (pwsh, danger-full-access)）
   → 提升会话沙箱模式到 danger-full-access
   → 写审计 SANDBOX_MODE_RAISED

⑤ 工具执行成功，tools/result
   → 标记上下文已结算（但不立即删除！见第 5 章坑 #3）

第二次调用（300 秒内，参数完全不同）
──────────────────────────────────────────────────────
模型: 我要执行 Get-ChildItem C:\other  （参数不一样，justification 也不一样）

① tools/pre-execute
   下游还是 allow → 透传

② tools/execute
   识别到升级请求 → 查 Lease → 【命中！】
   → 关键：这里 Guard 主动提升沙箱模式
   → 于是工具内部【根本不会触发审批】

结果：零弹窗。这就是"批准一次、后续免问"。
```

**这里有三个反直觉的关键点，面试时讲出来会加分**：
1. **审批不是在 `tools/pre-execute` 发生的**——那里永远返回 `allow`
2. **复用不是靠"拦截审批"实现的**——是在 `tools/execute` 抢先把模式提上去，**让审批根本不会发生**
3. **之所以不能在中途返回"批准"**——因为 `approval/request` 是开放的瀑布，人类答话器就在链上，你越过它 = 零交互自动批准一切（见 4.1）

## 4.1 亮点一：Universal Lease —— 补上 DSH 缺失的授权粒度

### 一句话主张

> **在不修改 DSH 源码、不改造任何既有工具的前提下，把"一次性批准"升级为"绑定 Session × Tool × Scope × TTL 的短期授权"，并保证原 `deny` 永不被覆盖。**

### 难点一：判断"该不该插手"的边界

Guard 必须**只增强、不取代**。具体规则：

```ts
// universal-gate.ts — handlePreExecute 的核心结构
// 第一步：先问下游（DSH 原生策略）的最终决策
const downstream = await next();

if (downstream?.kind === "deny") {
  // 原始拒绝永远透传，Lease 不得覆盖
  return downstream;
}
if (downstream?.kind === "allow") {
  // 放行不制造新审批
  return downstream;
}
if (downstream?.kind !== "ask") {
  return downstream;
}
// 只有 ask 才进入 Guard 的接管逻辑
```

**面试点**：为什么要先 `next()` 再判断？因为 Guard 是**外层中间件**（用 `prepend: true` 排在最前），必须拿到下游的最终决策才能判断"我该不该插手"。这保证了 DSH 原生语义的**优先级高于** Guard。

### 难点二：Scope 怎么定，才既安全又能复用

**默认太保守**：`exact-arguments` = `SHA-256(toolName + canonical JSON(arguments))`。

只有**参数逐字节相同**才能复用。为什么默认这么保守？

> 因为零配置情况下**无法可靠猜测**某个第三方工具的业务资源语义。
> 与其猜错导致授权面过大，**宁可多问一次**。

**但这里必须诚实**（面试时主动说）：
> "实测下来 LLM 几乎不会两次生成完全相同的参数——同一个文件路径会变、命令行会变、沙箱升级的 `justification` 是模型每次现写的。**所以零配置的默认收益其实有限**。真正省事的是显式配置 `sandbox-escalation` 或 `fields`。**收益来自显式配置，不是默认值。**"

**这句自我批评在面试里非常加分**——它证明你真的用过自己的东西。

### 难点三：并行调用的上下文隔离

Agent 可能**同时**发起多个工具调用。如果 Guard 用一个全局变量记录"当前会话/当前工具"，并行时就会串台。

**解法**：用 `callId`（DSH 为每次调用生成的唯一 id）作为键，维护一个 Map：

```text
PendingRegistry: Map<callId, PendingExecution>
```

**并且**要处理清理：
- `tools/result` 到达时删除
- `AbortSignal` 触发时删除（调用被取消）
- 兜底 GC：超过 10 分钟未结算的自动清理（防止内存泄漏）

### 关键代码

```ts
// pending.ts — 按 callId 隔离，且监听取消信号
set(entry: PendingExecution, signal?: AbortSignal): void {
  this.delete(entry.callId);
  this.entries.set(entry.callId, entry);
  if (signal) {
    const onAbort = () => this.delete(entry.callId);
    signal.addEventListener("abort", onAbort, { once: true });
    this.abortCleanups.set(entry.callId, () => signal.removeEventListener("abort", onAbort));
  }
}
```

### 怎么验证

- **负向测试**：`rejected` / `cancelled` / `unavailable` 三种结果都**不签发** Lease
- **deny 不可覆盖**：即使存在有效 Lease，下游返回 `deny` 仍然 `deny`
- **Session 隔离**：A 会话的 Lease 不能给 B 会话用
- **并行隔离**：两个 callId 的上下文不串台
- **跨路径一致性**：`pre-execute` 与 `tools/execute` 对同一次升级必须推导出**同一个 Scope key**（否则授权会静默失效）

### 面试追问与答法

**Q：这不就是在 DSH approval 外面套一层吗？**
> 不是套层。DSH 只有 preset（会话级、粗）和 `allowed-once`（单次、细），**中间那层是空的**。我补的是粒度，而且加上了 DSH 原生完全**没有**的两个性质：**自动过期**和**自动回滚**。

**Q：为什么不用 LLM 判断 Scope？**
> 那是把安全边界建立在模型输出上——模型可以被注入、可以不稳定。Scope 必须是**确定性函数**，输入相同输出必定相同。

**Q：`justification` 为什么不参与 Scope 计算？**
> 三重理由：① 它是模型现写的自由文本，参与就等于让模型决定授权边界；② 措辞一变授权立即失效，复用率几乎为零；③ 它可能包含敏感信息，不该进哈希。它只用于**给人看**（截断展示）。

## 4.2 亮点二：Sandbox Escalation —— 让授权真正生效的机制链

> **这是整个项目技术含量最高、也最能体现"深入机制"的部分。**

### 一句话主张

> **发现 DSH 的真实审批入口不在 `tools/pre-execute`（那里永远返回 `allow`），而在工具体内部的沙箱升级；据此重建授权链路，用「提升会话沙箱模式 + TTL 回滚」让短期授权真正产生效果。**

### 第一步：发现原设计是空转的（这是故事的核心）

**原设计假设**：DSH 原生策略会返回 `ask`，Guard 在 `tools/pre-execute` 接管它。

**去读真实源码后发现的事实**：

```js
// @deepseek-ai/dsh-tools/lib/index.js:3115-3116
const gate = await this.ctx.waterfall(carrier, "tools/pre-execute", exec,
  () => Promise.resolve({ kind: "allow" }));   // ← 落底决策就是 allow
```

Cordis 的瀑布语义（`cordis/lib/index.js:317-324`）：没有监听器认领时，**那个箭头函数本身就是最终决策**。

**穷尽清点随产品交付的监听器**（全量 grep）：

| 包 | 能否返回 `ask` |
|---|---|
| `dsh-hooks-claude-code` | **能**（但它不在默认组合里） |
| `dsh-hooks-codex` | 只能 `deny` |
| `dsh-tool-jobs` | 只 `return next()` |

而 `dsh-base/cordis.patch.yml:254` **只挂载了 `tool-jobs`**。

> **结论：在开箱即用的 DSH 中，`tools/pre-execute` 永远返回 `allow`。Guard 在那里等 `ask`，等于永远等不到——一个 Lease 都签不出来。**

### 第二步：找到真实入口

```js
// @deepseek-ai/dsh-sandbox/lib/index.js:93-104
const outcome = await approval.approver.request({
  agent: approval.agent,
  toolName: approval.toolName,
  callId: approval.callId,
  reason: `escalate sandbox to ${mode}: ${justification}`,
  ...
});
```

**这条路径的特点**：
1. 由 `pwsh` / `bash` / `fs` 三个工具的**内部代码**调用（`approveEscalation`）
2. 发生在 `tools/pre-execute` 决策**之后**（在 `dispatchToolBody` 里）
3. **载荷只有 `{agent, toolName, callId, reason, signal}`——不含 arguments！**

### 第三步：认清"授权签了也不生效"

即使签发了 Lease，**它本身不会改变 DSH 的沙箱判定**。沙箱该拒绝还是拒绝。

**必须调用 DSH 的公开 API 提升会话模式**：

```js
// @deepseek-ai/dsh-sandbox-policy/lib/index.js:41-43
function setSandboxMode(session, mode) {
  session.append("sandbox/mode", { mode });   // 写进持久 session log
}
```

**关键发现**：这个写入是**持久的**，而 DSH **原生没有任何过期机制**——一旦提升，要么永久留着，要么用户手动切回。

> **这正是本项目补上的洞：给沙箱模式变更加上 TTL 和自动回滚。**
> 这个定位比"减少审批点击"更硬——它是 DSH 真实缺失的能力。

### 第四步：解决"载荷没有 arguments"的问题

审批载荷不含参数，但签发 Lease 需要 Scope（"哪个工具的哪个档位"）。

**解法**：在 `tools/execute` 阶段**预先记录**上下文。

```ts
// universal-gate.ts — handleExecute（第 4 个 hook）
// tools/execute 是整条链路上唯一能同时拿到 callId 与 arguments 的时机：
// 它在工具体之前运行，且 exec.arguments 完整可用
const escalation = parseEscalation(exec.arguments);
if (escalation && sessionId) {
  const policy = this.deps.policy.resolve(exec.name);
  if (policy.enabled && policy.scope.mode === "sandbox-escalation") {
    const scope = this.deps.scopes.resolve({ toolName: exec.name, arguments: exec.arguments }, policy);
    this.escalations.set(exec.callId, { callId, sessionId, session, toolName, scope,
                                        requestedMode: escalation.requestedMode, ... });
    // 命中已有 Lease 则主动提升模式（复用路径）
    await this.reuseEscalationLease(exec, sessionId, scope.key, escalation.requestedMode, session);
  }
}
return await next();   // 始终原样返回，绝不改变结果
```

### 第五步：复用的正确实现（最反直觉的设计）

**错误做法**：在 `approval/request` 里发现"有有效 Lease"，就直接返回 `allowed-once`。

**为什么错**：`approval/request` 是**开放的瀑布**，DSH 自带的 UI 答话器就在链上。你提前返回 = **越过人类答话器** = 零人工交互自动批准一切。

**正确做法**：**在 `tools/execute` 抢先把模式提上去，让那次审批根本不会发生。**

```ts
// universal-gate.ts — reuseEscalationLease
const lease = await this.deps.leases.findMatching(sessionId, exec.name, scopeKey, "sandbox-mode");
if (!lease) return;   // 没命中，交给 DSH 原生审批
const applied = await grants.applyGrant({ leaseId: lease.id, sessionId, session, toolName, requestedMode });
// 提升成功后，工具体内部不会触发升级审批 → 无需合成任何 outcome
```

**这个设计同时满足了两个约束**：
- 守住了"绝不合成 outcome"的安全不变量
- 实现了"批准一次、后续免问"的产品价值

### 第六步：TTL 回滚与冲突检测（红线）

模式提升是持久的，所以必须回滚。但有个陷阱：**如果用户手动改过模式，回滚会冲掉用户的选择**。

```ts
// sandbox-grant.ts — releaseGrant 的冲突检测
const current = this.sandbox.sessionSandboxMode(grant.session);
// 以「Guard 对该 session 最后一次写入的值」为唯一基准比较
if (!grant.raised || !state || state.lastWritten === undefined) {
  return { outcome: "UNCHANGED", mode: current };
}
if (current !== state.lastWritten) {
  // 用户手动改过 → 不覆盖，交还控制权
  return { outcome: "SKIPPED_USER_OVERRIDE", mode: current };
}
```

**三个必须处理的边界情况**（都有测试）：

| 情况 | 处理 |
|---|---|
| 多条授权并存（宽的 + 窄的） | 释放宽授权时只降到"剩余需求最宽值"，**不降到 baseline** |
| 用户手动改过模式 | **跳过回滚**，记 `SANDBOX_MODE_SKIPPED_USER_OVERRIDE` 审计 |
| 窄授权（从未真正提升过）释放 | 返回 `UNCHANGED`，**不误报"用户改动"** |

### 关键代码：为什么"唯一 prepend"是硬约束

真 Cordis 实测（`integration/cordis-pipeline.test.ts`）：

```ts
// 两个 prepend 监听器的实测结果
root.on("evt", guardListener, { prepend: true });
root.on("evt", answererListener, { prepend: true });   // 后注册 → 排最前
// 结果：只有 answerer 被调用，guard 什么都看不到
// 原因：prepend 是 unshift（后注册在前）；认领（返回值不调 next）会终止整条链
```

> **这验证了两件事**：
> ① 如果在 handler 里直接返回 `allowed-once`，就会**越过人类答话器**（安全灾难）
> ② `approval/request` 上**只能注册一个 prepend 监听器**——多加一个（哪怕只为记日志）就会把 Guard 挤出观察位置，造成"审批通过却静默不签发 Lease"

### 怎么验证

| 验证项 | 方式 |
|---|---|
| 落底决策是 allow | 真 Cordis `waterfall` + 无 listener → 断言得到 `{kind:'allow'}` |
| 四 hook 接线 | 真 Cordis 装载插件，逐一验证行为 |
| 批准一次→免问 | 第二次调用用**完全不同的参数与理由**，断言零新增 Lease、零新增写入 |
| reject/cancel/unavailable | 三种非批准结果都不签发、不提升 |
| 到期回滚 | 推进时钟 → 下一次 `tools/execute` → 断言模式回落 + 审计有 `RESTORED` |
| 用户改动不覆盖 | 手动改模式 → 撤销 Lease → 断言模式未被回滚 + 审计有 `SKIPPED_USER_OVERRIDE` |
| 跨路径 key 一致 | `pre-execute` 签发的 Lease 能被 `tools/execute` 命中 |

### 面试追问与答法

**Q：你怎么知道原设计是错的？**
> 我没有"觉得"，我去读了本机安装版的编译产物（`lib/index.js`、`.d.ts`、`cordis.patch.yml`），逐行找到 `tools/pre-execute` 的落底决策，然后全量 grep 清点了所有随产品交付的监听器。**结论和我原来的假设相反。**

**Q：为什么不直接改 DSH 源码？**
> ① 违反项目规则（以独立插件接入）；② DSH 处于 Developer Preview 快速迭代，改源码升级即失效；③ 用公开 API 才是可持续的接入方式。

**Q：DSH 升级后你的结论还成立吗？**
> 不一定。所以我写了 `docs/集成基线-真实DSH行为.md`，每条结论带**文件+行号**引用，并有**升级后的重跑检查清单**（6 项）。这是可维护的做法，不是一次性结论。

**Q：两次错误假设的教训是什么？**
> **"接口存在"不等于"接口会走到"。** 我原来验证了 `pre-execute` 的**签名**正确，就以为接线对了——但那条路径在生产配置下根本不会产生 `ask`。**签名正确 ≠ 语义正确**，必须验证真实路径。

## 4.3 亮点三：Credential Broker —— 语义能力与凭证隔离

### 一句话主张

> **Managed Extension 不接触长期凭证：扩展只提交「业务操作」，由 Guard 校验 Lease、重算资源、解析凭证并调用 Provider；凭证只在 Guard 内部流转，绝不进入日志/审计/错误信息。**

### 难点一：怎么防"扩展伪造资源"

**攻击场景**：扩展注册时声明"我只会读 `repo:org/safe`"，但执行时提交"读 `repo:org/secret`"。

**双重校验**：Guard 用**可信 Runtime 产生的 `run.arguments`** 重新计算期望资源，与扩展自报的 `operation.resource` 比对。

```ts
// capability-service.ts — execute 的三重比对
const expectedResource = this.computeResource(definition, run.arguments);
if (operation.provider !== definition.provider) throw new GuardError("CAPABILITY_MISMATCH", ...);
if (operation.action !== definition.action) throw new GuardError("CAPABILITY_MISMATCH", ...);
if (operation.resource !== expectedResource) throw new GuardError("CAPABILITY_MISMATCH", ...);
```

**关键**：`resource` **不是扩展说了算**——Guard 会用扩展注册时提供的**同一个确定性函数**重算一遍。

### 难点二：凭证绝不出现在任何地方

**三重防线**：

1. **类型层面**：审计事件类型 `ToolAuditEvent` 里**根本没有参数原文字段**（只有 scope hash + 脱敏 display）
2. **出口脱敏**：Broker 捕获 Provider 抛出的任何错误，把消息中出现的凭证原文替换为 `***`
3. **每次重新解析**：不缓存凭证（这也是 DSH 自己的设计要求）

```ts
// broker.ts — 出口兜底脱敏：即使 Provider 误泄漏，也在边界处抹掉
function redact(text: string, secret: string): string {
  if (secret.length === 0) return text;
  return text.split(secret).join("***");
}
```

```ts
// broker.ts — per-operation 重新 resolve，绝不跨操作缓存
const service = this.deps.getCredentials();
if (!service) throw new GuardError("CREDENTIAL_NOT_CONFIGURED", "ctx.credentials unavailable");
resolved = await service.resolve(provider.credentialRef);
```

### 难点三：Provider 是可信代码，扩展不能注册

**规则**：Provider 由 Guard Core 内置/审核；Managed Extension **不得**注册能拿到 Secret 的 Provider。

**为什么**：如果扩展能注册 Provider，它就能注册一个"Provider"把凭证转发出去——Broker 就成了摆设。

### 必须主动说明的边界（面试红线）

> **Managed Mode 是架构约定，不是运行时强制。**
>
> 同进程的插件可以：
> - 直接读 `process.env`
> - 自己 `fetch` 绕过 Broker
> - 自己调 `setSandboxMode` / `approval.setPolicy` 改写权限状态
>
> **所以它的真实价值是"防误用 + 集中审计"**：让凭证只在一个可信路径里被解析、让外部调用留下统一记录、避免一个手滑的 `console.log` 泄漏凭证。**它不是防恶意的隔离边界。**

**面试时这段话必须说，而且要说得比面试官更清楚。** 把"架构约定"当成"安全边界"来宣传，是这类项目最常见也最危险的错误。

### 怎么验证

- Provider / Action / Resource 任一不一致 → `CAPABILITY_MISMATCH`
- Provider 未注册 → `PROVIDER_NOT_FOUND`
- Action 不在白名单 → `ACTION_NOT_ALLOWED`
- 凭证不可用 → `CREDENTIAL_NOT_CONFIGURED`
- Provider 超时 → `PROVIDER_TIMEOUT`
- **审计与错误信息中不含凭证原文**（负向测试）

### 面试追问与答法

**Q：既然能被绕过，这个 Broker 还有什么意义？**
> 三个真实价值：① **防误用**——按 SDK 写的扩展不会因为一个疏忽把凭证写进日志；② **集中审计**——外部调用只有一条路径，记录统一；③ **缩小分发面**——凭证只在一个模块里被解析，而不是散落在 N 个扩展里。这对应安全工程里的"减少攻击面"，不是"绝对防护"。

**Q：如果我要真正防恶意呢？**
> 那需要 OS 级隔离——独立进程、容器或 microVM，配合 IPC 边界。**那是另一个问题，本项目明确不提供**（DSH 原生 Sandbox 或外部机制负责）。诚实地划清边界比含糊地声称安全更重要。

# 第 5 章：踩过的坑

> **这一章是面试的黄金素材。** 面试官招的不是"一次写对的人"，是"错了能查出来并修正的人"。每个坑按 **现象 → 根因 → 修正 → 教训** 讲。

## 坑 #1：整个 Universal Mode 是空转的（最大）

**现象**：116 个测试全绿，代码看起来完整。但真实 DSH 里一个 Lease 都签不出来。

**根因**：设计假设"下游会返回 `ask`"。实际 `tools/pre-execute` 落底就是 `allow`，标准 profile 无监听器返回 ask。

**为什么测试没抓到**：测试自己造了 `const ask = () => Promise.resolve({kind:"ask"})` 直接喂给 handler——**验证了一个真实环境里不存在的场景**。而且 238 行测试里只有 1 个碰 `install()`，用的还是记录调用的假 bus。

**修正**：新增 `tools/execute` hook；把 `approval/request` 作为真实签发入口；补齐真 Cordis 集成测试。

**教训**：
> **测试通过 ≠ 系统能跑。** 单元测试验证的是**你假设的输入**，如果假设本身错了，测试只会加倍巩固错误。必须有测试覆盖"真实集成语义"，而不只是"我写的函数"。

---

## 坑 #2：有效授权被判定为失效，权限被错误回滚

**现象**：7 个测试失败，覆盖了 `sandbox-grant` 的多个授权场景，全是莫名其妙的断言错误。

**排查过程**：加探针 → 输出显示 `live false`，但打印出来的 Lease 明明是 `status: "ACTIVE"` 且 `expiresAt` 在未来。

**根因**：`settle()` 的默认参数用了**真实挂钟** `Date.now()`，而 Lease 是用**注入的可控时钟**创建的。两套时间基准比较 → `1.7e12 < 1.06e6` 为假 → 有效 Lease 被判失效。

**修正**：时间有效性只由 `LeaseManager.isLive(id)` **单一来源**判定，内部用自己的时钟；禁止调用方传入时间做安全比较。

**教训**：
> **可测试性设计（注入时钟）本身会引入新的一致性风险。** 一旦有多个地方能"看时间"，就会有多个时间基准。**安全判定必须有唯一时间源。**

---

## 坑 #3：`tools/result` 早于 `approval/request` 到达

**现象**：真 Cordis 集成测试里，"批准后应该签发 Lease"的断言失败，但探针显示审批结果确实是 `allowed-once`。

**根因**：我用 `tools/result` 作为"清理待批准上下文"的时机，但**实测存在 `tools/result` 早于 `approval/request` 到达的时序**。上下文被提前删掉，随后到达的审批找不到上下文 → 授权静默失效。

**修正**：`tools/result` **只标记结算时间**（`settledAt`），不立即删除；由一个有时限的宽限期（`ESCALATION_CONTEXT_GRACE_MS = 30s`）+ TTL 决定何时真正回收。

**教训**：
> **异步事件的顺序是分布式系统里最容易被假设错的东西。** "A 发生在 B 之后"必须验证，不能推理。**"清理"必须是幂等且可延后的**——早清理造成的通常是静默的功能失效（比崩溃更难查）。

---

## 坑 #4：两个 prepend 监听器互相遮蔽

**现象**：写真 Cordis 测试时，插件注册了 hook，但断言"注册了 4 个事件"失败——只看到 0 个。

**排查过程**：逐步缩小到最小实验 → 发现**两个都用 `prepend: true` 的监听器，后注册的排最前且会"认领"事件（返回值而不调 `next()`），先注册的完全收不到事件**。

**根因**：`prepend` 是 `unshift`（插入队首），所以后注册的 prepend 在最前；而瀑布中认领会终止整条链。

**修正**：写入项目宪法——**`approval/request` 上只允许注册这一个 prepend 监听器**，且必须是有条件转发 `next()` 的那一个。并加测试守护。

**额外的收获**：这条同时**验证了"绝不合成 outcome"的必要性**——如果在 handler 里直接返回 `allowed-once`，就会认领事件、越过人类答话器，构成**零交互自动批准**。

**教训**：
> **中间件的顺序语义必须实测，不能读文档想当然。** 而且这次实验意外发现了一条**安全红线**——错误的设计不只是"不工作"，可能是"静默地放行了所有请求"。

---

## 坑 #5：Cordis 的 Service 不能用属性访问

**现象**：插件装载测试报 `cannot get property "sessionProjections" without inject`。

**根因**：我原来用"形状探测"（`ctx.sessionProjections` 看有没有）实现降级。但 Cordis 的服务代理**对未经 `inject` 声明的属性访问直接抛错**。`inject` 是**硬依赖**，没有"可选注入"语法。

**修正**：改用 **`ctx.get(name)`**——缺失时返回 `undefined` 而不抛错，正是降级所需的语义。

**影响范围**：这个错误同时存在于 `buildSandboxContext`（沙箱模式读写）和 `findCredentialService`（凭证服务定位）。后者还**没有** try/catch 防护 `ctx.get` 抛错——被测试抓出来后补上。

**教训**：
> **假对象（fake ctx）会掩盖真实的框架约束。** 这个 bug 在我写了 30 多个测试之后才暴露，**只因为接了真框架**。凡是"与外部框架交互"的代码，必须有真框架的测试。

---

## 坑 #6：冲突检测的比较基准错了

**现象**：多条授权交替提升时，Guard 把**自己的写入**误判成"用户手动改动"，于是跳过回滚。

**根因**：我用**单条授权的 `writtenMode`** 做冲突检测。但后一条授权提升模式后，前一条的 `writtenMode` 就变成过期值，与实际模式不符。

**修正**：改为按 **session** 记录"Guard 最后一次写入的值"（`state.lastWritten`）作为**唯一比较基准**。

**教训**：
> **"最后一次写入"这类状态必须按正确的维度聚合。** 我按"授权"维度记，但语义上是"会话"维度的事实。**状态该挂在哪个实体上，是个需要想清楚的设计问题，不是随手选一个。**

---

## 坑 #7：我自己破坏了测试文件的编码

**现象**：用 PowerShell 的 `Set-Content` 批量替换测试代码后，文件变成**非法 UTF-8**，读都读不出来。

**修正**：改用文件编辑工具重写，并从此**不再用 shell 命令改源码文本**（批量文本替换在含中文/特殊字符的代码上风险极高）。

**教训**：
> **工具选择本身是工程判断。** 用 shell 做批量文本替换"看起来快"，但在非 ASCII 内容上会静默损坏文件。**该用专用工具就別图省事。**

---

## 坑 #8（实现细节）：`settle()` 的调用顺序导致模式永远升不上去

**现象**：同一 session 内连续授权时，模式提升总是失败。

**根因**：`settle()`（清理失效授权）排在"幂等检查"之后，把**本次刚记录的授权**当成失效项回收了。

**修正**：`settle()` 必须先执行，再做幂等与提升判断。

**教训**：
> **"清理"和"使用"的顺序是经典的时序陷阱。** 清理代码必须是"只清理确定已死的"，而且要能证明它不会误伤刚创建的对象。

---

| **并发/时序/一致性** | 3 | #2（双时钟）、#6（聚合维度）、#8（清理顺序） |

# 第 6 章：开发经验与方法论

## 6.1 最重要的一条：验证"真实路径"，而不是"接口签名"

**这个项目最大的教训，也是最有价值的方法论。**

我原来验证了 `tools/pre-execute` 的**签名**（参数、返回值类型都对），就认为接线正确。但真实配置下**那个 `ask` 永远不会出现**。

**正确做法**：
1. 找到**真实调用点**（不是我预期的调用点）：`dsh-tools/lib/index.js:3115`
2. 读**落底行为**：默认返回什么？
3. **穷尽清点**谁会打破默认：全量 grep 所有 listener
4. 找到**生产配置**实际挂了哪些

**沉淀为项目规则**：任何关于 DSH 行为的结论，必须**带文件+行号**写入基线文档，并有**升级后重跑清单**。

## 6.2 测试分层：单元测试之外必须有集成测试

| 层次 | 验证什么 | 局限 |
|---|---|---|
| 单元测试（204 个） | 我的算法逻辑对不对 | **验证的是我假设的输入** |
| **真框架集成测试** | 接线语义对不对 | 需要真依赖（`@deepseek-ai/cordis`） |
| **离线组合验证** | 配置能否被真实加载 | `dsh --dump-config --patch` |

**关键实践**：真框架测试**一次性抓出了 3 个单元测试永远发现不了的 bug**（坑 #3 #4 #5）。

## 6.3 负向测试优先

安全代码的价值**不在"正常时能工作"，而在"异常时不开后门"**。

本项目的负向测试覆盖：

- `rejected` / `cancelled` / `unavailable` 三种非批准结果 → 不签发
- `deny` 不可被 Lease 覆盖
- 跨 session 的批准 → 拒绝接管
- 已消费的上下文被重放 → 不重复签发
- 服务缺失 → 降级为"不动权限"，而不是抛错打断
- 凭证不出现在错误信息/审计里

## 6.4 把"边界"写进文档，比写功能更重要

本项目的文档里最长的不是功能列表，而是**"我不能承诺什么"**：

- 不能防恶意插件（Managed Mode 是约定）
- 不能阻止其他插件认领 `approval/request`
- 子 Agent 无法受益
- 不提供 OS 级隔离

**为什么**：把"架构约定"当"安全边界"宣传，是这类项目最危险的错误。**主动划清边界反而提升可信度。**

## 6.5 不变量要用测试守护，不能只写在注释里

例：`approval/request` 处理器"绝不合成 outcome"。

**光写注释不够**——后来者（包括未来的我）可能为了某个功能破坏它。所以用测试钉死：

```ts
// 用 Object.freeze 的 sentinel 断言：返回值与下游结果必须是【同一个引用】
const sentinel = Object.freeze({ decision: "allowed-once" });
const out = await gate.handleApprovalRequest({ callId: "c1" }, spy);
expect(out).toBe(sentinel);        // 全等，不是"相等"
expect(spy).toHaveBeenCalledTimes(1);   // next() 只调用一次
```

**四个用例覆盖四种结果 + 无 pending 透传 + 签发失败不改写。**

## 6.6 经验：先做能立刻验证的最小闭环

面对"设计整个授权体系"这种大任务，我没有一次写完，而是：

1. **先做纯逻辑模块**（`escalation.ts`：识别升级请求 + 生成 Scope key）——不依赖任何宿主，立刻可测
2. **再做可独立测试的状态机**（`sandbox-grant.ts`：提升/回滚/冲突检测）——注入 I/O 接口，16 个测试
3. **最后接进真实 hook**——此时逻辑已经被证明，问题只可能出在接线

**收益**：8 个坑里有 5 个是在第 1、2 步就暴露的（那时修复成本极低）。

# 第 7 章：面试专项

## 7.1 90 秒自我介绍模板

> "我做的项目叫 DSH Capability Guard，是给 DeepSeek Harness 这个 Agent 框架补权限中间层的插件。
>
> 起因是我观察到 DSH 的权限模型有两层：会话级的 preset 太粗，单次的 `allowed-once` 每次都问——**中间那层是空的**。Claude Code 和 Codex 用静态配置补这层，但静态配置没有过期、没有自动回收、没有"什么时候放宽过"的记录。我用运行时的 Lease 来补：一次批准变成绑定 `Session × Tool × Scope × TTL` 的短期授权，到期自动失效并回滚。
>
> 项目过程中最重要的是一个**认知修正**：我原本假设 DSH 在 `tools/pre-execute` 会返回 `ask`，写了 116 个测试全绿。但我后来去读了本机安装版的编译产物，发现**那里的落底决策永远是 `allow`**——标准 profile 下没有任何监听器返回 ask。也就是说我的设计在真实环境里**一个授权都签不出来**。
>
> 我因此重建了整条链路：找到真实的审批入口是工具内部的沙箱升级，用第四个 hook `tools/execute` 在参数还可用时记录上下文，批准后签发授权**并提升会话沙箱模式**——因为 Lease 本身不改变 DSH 的判定。到期时回滚，并且检测用户是否手动改过、改过就不覆盖。
>
> 现在有 214 个测试，其中包括用**真实 cordis** 跑的集成测试——正是它帮我抓出了三个单元测试永远发现不了的 bug。"

**为什么这个模板有效**：它把"我做了个插件"变成了"我发现假设错了、查明真相、重建系统"。**后者是面试官真正想听的。**

## 7.2 三个简历点（可直接复制）

> **1. 设计并实现 Agent 权限中间层（Universal Lease）**
> 针对 Agent 平台"审批粒度只有会话级与单次级"的缺口，设计绑定 `Session × Tool × Scope × TTL` 的运行时短期授权：确定性 Scope 生成（禁止用 LLM 猜边界）、并行调用 callId 隔离、Fail-Closed 语义、deny 永不被覆盖。纯 TypeScript，零运行依赖。

> **2. 逆向核实宿主行为并重建沙箱授权链路（Sandbox Escalation）**
> 通过逐行阅读宿主编译产物，发现原设计依赖的审批路径在生产配置下不产生 `ask`（落底决策为 `allow`），据此重建链路：新增 `tools/execute` hook 捕获上下文、以 `(工具, 目标档位)` 生成语义 Scope、批准后提升会话沙箱模式、TTL 到期自动回滚并做用户改动冲突检测。

> **3. 实现凭证代理与语义能力校验（Credential Broker）**
> Managed Extension 不接触长期凭证：由 Guard 从可信运行上下文重算资源并做 provider/action/resource 三重比对，阻止扩展伪造资源；per-operation 重新解析凭证、出口错误脱敏、审计类型层面不含参数原文，并诚实声明其为架构约定而非运行时隔离边界。

## 7.3 高频问题与标准答法

### A 类：质疑项目必要性

**Q：这不就是给 approval 套个壳？平台自己不能做吗？**
> 平台**能**做，但它没做——DSH 目前只有会话级 preset 和单次 `allowed-once`。而且它缺的不只是粒度，还有**过期与自动回滚**：沙箱模式的写入是持久的，原生没有任何机制让它自动恢复。
> 我做的是**用公开 API 补这个缺口**，不修改宿主源码，因此 DSH 升级也不会失效。

**Q：用户直接开全权限模式不就行了？**
> 那正是问题所在——**审批疲劳会把人逼到关掉所有审批**。这不是安全，是"安全机制因为太烦而被绕过"。有界授权给了中间选项：**既不是每次问，也不是全放开。**

### B 类：质疑安全性

**Q：恶意插件能绕过吗？**
> 能。Managed Mode 是 SDK 约定 + 代码评审保证的**架构约束，不是运行时强制**。同进程插件可以直接读环境变量、自己发网络请求、自己调用权限改写 API。
> 所以它的价值是**防误用 + 集中审计**：凭证只在一个可信路径被解析、外部调用有统一记录。**真正的运行时边界是 DSH 进程本身**，要强隔离需要容器或独立进程。

**Q：那你的安全声明是不是过度了？**
> 我在 README 和管理文档里专门写了一节"关于边界的如实说明"，明确列出我**不能**承诺什么。把架构约定当安全边界宣传是这类项目最常见的错误，我不想犯。

**Q：`approval/request` 上你排在最前，如果写错了会怎样？**
> 会很严重——**零人工交互批准一切，并旁路人类答话器**。所以我把它做成不变量：任何路径都必须 `await next()` 并**原样返回**其结果，方法体内禁止出现 `"allowed-once"` 返回值。并且用 sentinel 全等断言 + 四种结果覆盖的测试守护它。
> 真 cordis 测试还额外发现：如果再加一个 prepend 监听器，会把 Guard 挤出观察位置，导致"审批通过却静默不签发授权"。这条也写进了项目规则。

### C 类：技术深度

**Q：为什么不缓存凭证？**
> ① 凭证可能轮换，缓存会导致用旧凭证；② 缓存意味着内存里长期驻留密钥，扩大泄漏面；③ **DSH 自己的设计文档就明确要求 per-operation resolve、不得跨操作缓存**——我遵循宿主的契约。

**Q：并行工具调用怎么保证不串台？**
> 用 `callId` 作为键维护上下文 Map，禁止任何全局的"当前会话/当前工具"变量。同时监听 `AbortSignal` 处理取消，并用超龄 GC 兜底防止内存泄漏。

**Q：TTL 到期怎么保证及时回滚？**
> **不依赖定时器。** 安全正确性靠读写时实时比较时间（单一时间源），低频 GC 只做内存回收。回滚发生在下一次 `tools/execute` 的结算阶段——**这是"收缩权限"方向，晚执行不会造成越权**。

**Q：怎么防止同一 callId 的审批被重放，导致重复签发？**
> 批准后立即从表中移除该升级上下文（用掉即失效）。有专门的测试断言重放不会产生第二条 Lease。

**Q：如果用户手动改了沙箱模式，你的回滚会不会冲掉？**
> 不会。回滚前做冲突检测：当前模式如果**不等于 Guard 最后一次写入的值**，说明用户改过，**跳过回滚**并把控制权交还用户，同时写 `SANDBOX_MODE_SKIPPED_USER_OVERRIDE` 审计。

### D 类：工程能力

**Q：测试怎么组织的？**
> 三层：① 204 个单元测试（算法与负向路径）；② 20 个**真 cordis** 集成测试（接线语义、瀑布认领、插件装载、服务解析语义）；③ 离线组合验证（`dsh --dump-config --patch` 检查配置能否被真实加载）。
> 第二层是关键——它抓出了 3 个单元测试永远发现不了的 bug（事件时序、prepend 遮蔽、服务访问方式）。

**Q：如果重做一遍，你会先做什么？**
> 先读宿主的真实运行路径，再动手设计。我会把"接口签名核对"和"生产路径核实"分成两件事——我原来只做了前者。

**Q：这个项目最大的收获是什么？**
> **"接口存在"不等于"接口会走到"。** 8 个坑里只有 1 个是写代码手滑，其余都是对系统行为的理解偏差。所以我现在会先问"这条路径在生产配置下真的会触发吗"，而不是"这个函数的签名对不对"。

# 第 8 章：自测题库

> **用法**：先自己答，再看参考答案要点。答不出来的回对应章节。

## 第一层：定位与动机（必须脱口而出）

**Q1. 用一句话说这个项目解决什么问题？**
<details><summary>要点</summary>
DSH 权限模型只有会话级 preset（太粗）与单次 allowed-once（每次都问），中间那层是空的；本项目用运行时 Lease 补上，并加上 DSH 原生没有的过期与自动回滚。
</details>

**Q2. 为什么说"审批疲劳"是个安全问题，不只是体验问题？**
<details><summary>要点</summary>
因为它会把人逼到关掉所有审批。一个因为太烦而被绕过的安全机制等于没有。有界授权提供了中间选项。
</details>

**Q3. 和 Claude Code 的 permissions 配置有什么本质区别？**
<details><summary>要点</summary>
静态配置 vs 运行时对象。静态配置写死在文件里：改要重启、没有过期、没有自动回收、没有"何时放宽过"的记录。Lease 是活的：有签发时间/过期时间/状态机/可撤销/被审计。
</details>

**Q4. 项目**不**解决什么？**
<details><summary>要点</summary>
① 不防恶意插件（Managed Mode 是架构约定非运行时强制）；② 子 Agent 无法受益（DSH 把它的 approval policy 钉死为 never）；③ 不提供 OS 级隔离。运行时强制边界是 DSH 进程本身。
</details>

## 第二层：机制（技术面试主战场）

**Q5. 画出四 hook 的职责与顺序。**
<details><summary>要点</summary>
`tools/pre-execute`（只接管下游 ask，生产环境通常 allow 透传）→ `tools/execute`（识别升级、记上下文、复用提升模式）→ `approval/request`（只观察、绝不合成 outcome）→ `tools/result`（标记结算）。
</details>

**Q6. 为什么真实审批不在 `tools/pre-execute`？**
<details><summary>要点</summary>
因为它的落底决策就是 allow（`dsh-tools:3115-3116`），而标准 profile（`dsh-base/cordis.patch.yml:254`）只挂载了 tool-jobs，没有任何随产品交付的监听器返回 ask。真实审批来自 pwsh/bash/fs 工具体内部的 approveEscalation。
</details>

**Q7. 为什么复用授权要在 `tools/execute` 而不是在 `approval/request` 返回"批准"？**
<details><summary>要点</summary>
两个理由：① `approval/request` 是开放瀑布，DSH 自带 UI 答话器就在链上，提前返回 = 越过人类答话器 = 零交互自动批准一切；② 在 `tools/execute` 抢先把沙箱模式提上去，让那次审批根本不发生——同样达到"免问"效果，却不破坏安全不变量。
</details>

**Q8. 为什么 Lease 签了还不够，还要提升会话沙箱模式？**
<details><summary>要点</summary>
因为 Lease 是本插件内部的对象，不影响 DSH 的沙箱判定。必须调 `setSandboxMode(session, mode)` 才能真正生效；而这个写入是持久的、DSH 原生没有过期机制——所以必须由本项目补 TTL 回滚。
</details>

**Q9. `(toolName, 目标模式)` 为什么比参数哈希更适合沙箱升级？**
<details><summary>要点</summary>
因为升级场景的参数几乎不可能复用：命令不同、`justification` 是模型每次现写的。按参数哈希等于每次都要重新问。按 (工具, 档位) 取键的语义恰好是"本会话内该工具可以升到这一档"，与用户批准时的心理模型一致。
</details>
**Q10. 为什么 `justification` 绝不能参与 Scope 计算？**

<details><summary>要点</summary>
它是模型现写的自由文本。参与就等于让模型决定授权边界（可被注入、不稳定）；措辞一变授权立即失效；可能含敏感信息。它只用于给人看（截断展示）。
</details>

**Q11. 两个 prepend 监听器会怎样？为什么这是安全问题？**
<details><summary>要点</summary>
后注册的 prepend 排最前，认领事件（返回值不调 next）会终止整条链，先注册的完全收不到。安全隐患：① 如果 Guard 在 handler 里返回 allowed-once，就是零交互批准一切并旁路人类答话器；② 任何额外的 prepend 会把 Guard 挤出观察位置，造成"审批通过却静默不签发授权"。
</details>

**Q12. Cordis 里为什么不能用 `ctx.foo` 访问服务？**
<details><summary>要点</summary>
未经 inject 声明的服务，属性访问会被 cordis 代理抛 `cannot get property … without inject`。必须用 `ctx.get(name)`（缺失返回 undefined，不抛错）。inject 是硬依赖，没有可选注入语法，所以"缺失即降级"只能靠 ctx.get。
</details>

## 第三层：安全与正确性

**Q13. 默认 Scope 是 `exact-arguments`，这够用吗？**
<details><summary>要点</summary>
诚实说：不够。LLM 几乎不会两次生成完全相同参数，所以零配置收益有限。默认保守是为了不越权（无法可靠猜测第三方工具的业务语义），**真正省事的是显式配置 `sandbox-escalation` 或 `fields`**。
</details>

**Q14. 怎么保证 TTL 到期后权限真的收回？**
<details><summary>要点</summary>
不依赖定时器。① 安全判定靠读写时实时比较时间（单一时间源 `LeaseManager.isLive`，用自身时钟）；② 沙箱模式回滚在下一次 `tools/execute` 的结算阶段执行——这属于"收缩权限"方向，晚执行不会造成越权；③ 低频 GC 只做内存回收。
</details>

**Q15. 用户手动改了模式，你的回滚会不会覆盖他的选择？**
<details><summary>要点</summary>
不会。以"Guard 对该 session 最后一次写入的值"为唯一基准比较；不等则跳过回滚，记 SKIPPED_USER_OVERRIDE 审计。
</details>

**Q16. 为什么不能用单条授权的 writtenMode 做冲突检测？**
<details><summary>要点</summary>
多条授权交替提升时，后一条会改写模式，使前一条的 writtenMode 成为过期值，从而把 Guard 自己的写入误判为用户改动。必须按 session 维度记录最后写入值。
</details>

**Q17. 怎么防止 callId 的审批被重放，重复签发？**
<details><summary>要点</summary>
批准后立即从升级上下文表中移除该条目（用掉即失效）。有测试断言重放不产生第二条 Lease。
</details>

**Q18. 假设有恶意插件，它能做什么？你的防御是什么？**
<details><summary>要点</summary>
它能：读 process.env、自己 fetch、自己调 setSandboxMode/approval.setPolicy 改写权限状态、甚至抢先认领 approval/request 返回假批准。本项目的防御**不是**阻止它，而是：凭证集中解析 + 审计留痕 + 明确的边界声明。**要真隔离需要 OS 级机制。**
</details>

## 第四层：工程与反思（区分度高）

**Q19. 你最大的 bug 是什么？怎么发现的？**
<details><summary>要点</summary>
整个 Universal Mode 是空转的：116 个测试全绿，但真实 DSH 里一个 Lease 都签不出来。发现方式：去读本机安装版的编译产物，逐行确认落底决策是 allow，再全量 grep 清点所有 listener，最后确认生产配置只挂了 tool-jobs。测试没抓到的原因：测试自己造了 ask 输入，验证了一个真实环境不存在的场景。
</details>

**Q20. 为什么单元测试没抓到那些 bug？**
<details><summary>要点</summary>
单元测试验证的是"我假设的输入"。假设错时，测试只会加倍巩固错误。真框架集成测试抓出了 3 个单元测试发现不了的 bug：tools/result 早于 approval/request 的时序、prepend 互相遮蔽、服务必须用 ctx.get。
</details>

**Q21. 单一时间源那条教训是怎么来的？**
<details><summary>要点</summary>
注入可控时钟是为了可测试性，但 `settle()` 的默认参数用了真实挂钟，与 Lease 的注入时钟形成两套基准，导致有效 Lease 被判失效（1.7e12 < 1.06e6 为假）。修正：安全判定只能有一个时间来源。
</details>

**Q22. 如果重做，你会改变什么？**
<details><summary>要点</summary>
先核实宿主的真实运行路径，再设计。把"接口签名核对"和"生产路径核实"分成两件事——我原来只做了前者就以为接线正确了。
</details>

**Q23. 这个项目你觉得还差什么？**
<details><summary>要点</summary>
① 真实 profile 端到端实跑（未做）；② read-only → workspace-write 跨档路径未实测；③ 性能开销未量化（settleAll 每次 tools/execute 都跑）；④ 跨会话授权未支持（与"Lease 必绑 session"规则冲突，需设计权衡）；⑤ Audit 目前是内存实现，重启即失，合规场景需要持久化。
</details>

**Q24. 你从这个项目学到最重要的一件事？**
<details><summary>要点</summary>
"接口存在"不等于"接口会走到"。8 个坑里只有 1 个是写代码手滑，其余都是对系统行为的理解偏差——所以现在我会先问"这条路径在生产配置下真的会触发吗"，而不是"这个函数签名对不对"。
</details>

## 附录 B：一页速记（面试前一晚看这个）

```text
【定位】DSH 权限模型缺中间层 → 用运行时 Lease 补，并加过期与自动回滚

【四 hook】pre-execute(接管 ask，生产多为 allow)
         → execute(识别升级+复用提升)  ← 关键
         → approval/request(只观察，绝不合成)
         → result(标记结算)

【核心事实】pre-execute 落底 = allow（dsh-tools:3115）
          真实审批 = 工具体内 approveEscalation（dsh-sandbox:93）
          载荷不含 arguments → Scope 必须在 execute 阶段算

【复用原理】不在 approval 里返回批准（会越过人类答话器）
          而是在 execute 抢先把沙箱模式提上去，让审批根本不发生

【红线】① 只观察不合成 outcome
       ② 只用 setSandboxMode，禁用 permissionPresets.set（会关掉审批）
       ③ 回滚前检测用户改动，改过就跳过
       ④ 不为子 session 签发

【三个边界】不防恶意 / 子 Agent 无收益 / 无 OS 隔离

【一句教训】接口存在 ≠ 接口会走到

【待办】真实 profile 端到端实跑 + 录像
```
