### 1.0.1 下次启动后的第一件事：读 routes 状态

```powershell
(Invoke-WebRequest http://127.0.0.1:8787/api/config -UseBasicParsing).Content | ConvertFrom-Json | Select-Object -ExpandProperty routes
```

三种结果分别意味着：

| 结果 | 含义 | 下一步 |
|---|---|---|
| `registered: true` | 同源入口已就绪（重试补上了） | 直接用 Web GUI 面板，无需再管 |
| `registered: false, serviceSeen: true` | 能拿到 webServer，但注册被拒（路径冲突） | 看 `error` 字段，换前缀即可 |
| `registered: false, serviceSeen: false, retries: 6` | 本插件的 ctx 始终看不到 webServer | 改用「首次工具活动时注册」的方式（不依赖启动窗口），不要再加重试 |

## 1.1 为什么必须重启 DSH

安装 bundle 时 profile 通过 HMR 重组了配置（行已生效，四个 hook 已挂上，治理台已监听 8787），
但 **HMR 只重组配置，不会重新加载已装载模块的新一代 JavaScript**（`dsh-hmr` 源码：`import()` 新代
之前清缓存，但只对"被接受的文件变更"触发，且忽略 `node_modules`）。因此：

- 现在进程里跑的是**首轮装载的旧代码**：没有 loopback CORS、也没有 `ctx.inject` 等待；
- 浏览器打开 `http://127.0.0.1:8787/` 可用（同源，不需要 CORS）；
- Web GUI 面板能点开、能看到图标，但会因为跨源被拦而显示"尚未连接"；
- 重启 DeepSeek Harness 后，上面两条 ⚠️ 会自动变成 ✅（代码已就绪且有测试守护）。

重启后的自检（三条都应通过）：

```powershell
# ① 同源路由就绪
Invoke-WebRequest http://127.0.0.1:19387/guard/api/config -UseBasicParsing | Select-Object StatusCode
# ② 独立端口 + CORS（Origin 为 loopback 时应回显）
(Invoke-WebRequest http://127.0.0.1:8787/api/snapshot -UseBasicParsing -Headers @{Origin='http://127.0.0.1:19387'}).Headers['Access-Control-Allow-Origin']
# ③ 面板入口仍注册
#    用 cordis_inspect_query: platform=client provider=Slots method=listSubTree root=sidebar.panellist
#    期望 occupants 里同时有 plugins 与 guard
```

## 3. 怎么手动验证一次完整生命周期

### 3.1 沙箱升级链路（最有价值的一条）

1. 在 GUI 里把会话权限档位设成 **workspace-write**（默认），审批策略保持 **ask**；
2. 让 Agent 执行一次越出工作区的写入（模型会带 `sandbox_permissions: danger-full-access` + `justification` 重试）；
3. 弹出审批 → 批准一次；
4. 打开 http://127.0.0.1:8787/ ，「授权与剩余时间」里应出现一条 `kind=sandbox-mode`、
   scope 为 `沙箱升级至 danger-full-access` 的授权，倒计时实时递减；
5. 让 Agent 再执行一次**同类**升级（参数与理由可以完全不同）→ 不再弹审批；
6. 等 TTL 到期（默认 300s）后再执行任意一次 pwsh → 档位回滚到批准前的值；
   「审计」里能看到 `SANDBOX_MODE_RAISED` → `SANDBOX_MODE_RESTORED`。

> 如果第 5 步仍然弹审批：说明会话档位没被提升（`ctx.sessionProjections` 缺失或会话对象不可达）。
> 该链路是**失败即回落原生审批**，不会越权。

### 3.2 审批策略必须是 ask

`approval policy = never` 时，DSH 在瀑布派发**之前**就把审批判成 `rejected`，Guard 根本收不到事件，
不会有任何授权签发。这是设计使然（Guard 不绕过 Approval），不是缺陷。

## 4. 出问题看哪里

| 现象 | 排查 |
|---|---|
| 治理页面打不开 | 端口是否被占用（stderr 打印的 `[dsh-guard] governance console: …`）；`console.enabled` 是否为 false |
| 面板显示「尚未连接到治理接口」 | 同源 `/guard/` 与 8787 起 4 个端口都没响应；先确认独立页面能打开，再看浏览器控制台的 CORS/404 |
| 审计里只有 `PASSTHROUGH_ALLOW` | 正常：standard profile 的 `tools/pre-execute` 落底就是 allow；只有沙箱升级会产生 ASK→LEASE |
| 改了代码没生效 | 见 2.2：HMR 不换 JS 代，必须重启 |

## 5. 安全边界（不要越界实现）

- 治理台的写接口**只能**改 `defaultScope` / `defaultTtlSeconds` / `maxTtlSeconds`；
  `enabled` 与 `rules` 永远返回 400（页面不能关掉 Guard，也不能凭空造授权规则）。
- `tool` 挡位禁止作为默认值（规格第 7 条），接口层与 UI 下拉都禁用它。
- 运行时改动**不落盘**：不擅自改写 profile 的 `cordis.patch.yml`（那是用户与 DSH 插件管理器的地盘），
  重启后回到 profile 配置值。
- 面板不做任何审批 / 撤销 / 签发动作。
